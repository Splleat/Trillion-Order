# 보상 트랜잭션은 어떻게 보상하나?

## 1. 배경 - 주문 서비스가 죽으면? 

분산 트랜잭션 구현이 어느 정도 마무리됐다고 생각하던 시점에 팀원이 물었다. "여기서 서버가 멈추면 어떻게 되나요?" 그 질문 하나가 주문 서버가 다시 재시작한 뒤 보상 트랜잭션을 처리할 스케줄러 구현의 시작이었다.

주문 생성 도중에 주문 서버가 예기치 못한 이유로 종료되거나 재배포로 재시작되면 실행 흐름이 그대로 끊긴다. 문제는 크게 두 가지로 나타났다. 

1. 트랜잭션 중단: 도서 서비스에서 재고 차감은 완료되었지만, 주문 서비스가 다음 단계인 쿠폰 사용 API를 호출하기 전에 종료되었다. 이 경우 재고 차감은 이미 커밋되었기 때문에 자동으로 롤백되지 않으며, 중단된 사가를 복구할 별도의 처리가 필요했다. (이전 문서에서 도서 API -> 쿠폰 API -> 포인트 API 흐름을 기록하는 엔티티가 사가이다)
2. 최종 반영 유실: 분산 트랜잭션 흐름은 모두 성공했는데, 주문 엔티티에 반영하기 이전에 문제가 생겨 주문 생성 사가는 완료되었지만, 주문 엔티티는 여전히 초기 생성 상태인 불일치 상태

이런 데이터들은 스스로 복구되지 않는다. 주기적으로 주문의 상태를 스캔하고 보정하는 스케줄러가 필요한 이유였다.

## 2. 복구 방식 선택

주문의 상태를 DB에 저장해 조회하는 방식을 선택했다. 이벤트를 발행하는 방식도 검토했지만, 영속화가 가능한 메시지 큐를 사용하지 않는 이상 서버가 중단되면 이벤트 자체를 발행할 수 없고, 발행하더라도 서버가 중단되면 그대로 휘발된다. 결국 주문 서버 재시작 후 시점을 생각하니 DB에 저장된 주문의 상태를 기준으로 삼는게 가장 신뢰할 만하다고 생각했다.

별도의 배치 서버 없이 Spring Scheduler를 사용해서 주기적으로 DB를 폴링하는 스케줄러를 구현했다. 그런데 당시 모든 마이크로서비스는 무중단 운영을 위해 이중화되어 있었고, 주문 서비스도 마찬가지로 이중화가 되어 있었다. 두 주문 서비스가 동시에 하나의 주문을 복구하면 중복 보상이 발생할 수 있었다. 그래서 분산 락이 필요하다는 것을 알게 되었는데, Redis를 사용하는 Redisson과 DB를 사용하는 ShedLock이 있었다. 추가적인 설정이 필요한 Redisson보다 바로 사용할 수 있는 ShedLock을 선택하게 되었다.

## 3. 스케줄러 설계

복구가 필요한 케이스를 생각해보니 3가지였다. 중단된 사가, 사가는 완료되었지만, 주문 엔티티에 반영되지 않은 경우, 결제 없이 장기간 대기 중인 주문(`PENDING`, 결제 대기)이었다.

하지만 단순히 상태가 `PROGRESS`인 사가를 모두 가져오면 안된다. 스케줄러가 정상적으로 처리 중인 요청의 사가를 낚아채 롤백해버리는 경쟁 상태가 발생할 수 있기 때문이다. 그래서 쿼리 조건에 `updatedAt < NOW - 1분`을 추가했다. 주문 생성 흐름 자체가 1분을 넘길 수 없다는 전제에서 나온 기준이다. 1분이 지나도 상태 변화가 없다면 정상 처리 중인 요청이 아니라 중단된 것으로 판단한다. (스케줄러는 5분마다 작동한다)

### 복구 정책

| 시나리오            | 대상                                        | 상태                         | 동작       | 근거                                                                       |
|:----------------|:------------------------------------------|:---------------------------|:---------|:-------------------------------------------------------------------------|
| 주문 생성 중단        | `OrderCreateSaga`                         | `PROGRESS` / `COMPENSATED` | 롤백       | 1분이 경과한 사가는 멈춘 것으로 판단                                                    |
| 주문 취소 중단        | `OrderCancelSaga`                         | `PROGRESS` / `FAILED`      | 재시도      | 주문 취소를 취소하는 것은 다시 주문을 생성하는 것 -> 모순                                       |
| 주문 환불 중단        | `OrderItemRefundSaga`                     | `PROGRESS` / `FAILED`      | 재시도      | 주문 취소와 동일한 이유                                                            |
| 도메인 미반영 (생성)    | `OrderCreateSaga`                         | `COMPLETED`                | 롤백       | 주문 생성 사가가 `COMPLETED`라는 것은 주문 전체가 완료된 것이 아닌 도서, 회원, 쿠폰 서비스에 대한 작업만 완료된 것 |
| 도메인 미반영 (보상)    | `OrderCreateSaga`                         | `COMPLETED_COMPENSATED`    | 도메인과 동기화 | 보상 트랜잭션은 완료됐으나 도메인에 미반영된 상태 -> 동기화                                       |
| 도메인 미반영 (취소/환불) | `OrderCancelSaga` / `OrderItemRefundSaga` | `COMPLETED`                | 도메인과 동기화 | 주문 취소가 성공했으면 엔티티와 동기화                                                    |
| 미결제 장기 대기       | `Order`                                   | `PENDING` + 1시간 경과         | 롤백       | 1시간 이상 선점된 재고·쿠폰·포인트를 강제로 회수                                             |

처음에는 주문 생성 사가도 주문 취소 사가처럼 재시도를 통해 주문 엔티티를 완성할 생각이었다. 하지만 스케줄러가 해당 사가를 잡는 시점은 사용자가 주문 생성 버튼을 누르고 1분 이상이 지난 비정상적인 시점으로, 서버 에러로 사가가 정상적으로 처리되지 못했을 것이다. 이 상태에서 주문을 다시 생성을 하면 사용자가 이전 주문을 실패로 인식하고 다시 주문을 하게 되어 동일한 상품에 대한 주문이 두 번 접수되는 문제가 발생할 수 있다고 생각했다. 

취소와 생성은 다르다. 사용자가 취소를 선택한 순간, 해당 주문은 취소의 취소가 불가능한 최종 상태이다. 실패를 이유로 취소를 취소하면 다시 주문을 생성하는 모순적인 상황이 된다. 만약 주문 취소를 취소해 다시 주문을 생성하는 상황이라면, 차감했던 재고, 포인트, 쿠폰을 다시 점유해야 하는데, 그 사이 사용자가 이 자원들을 다른 주문에 사용하게 된다면 주문 취소를 취소하는 것도, 주문 취소를 취소하는 것을 취소하는 것도 불가능해진다. 그래서 주문 생성은 롤백, 취소와 환불은 재시도로 분리했다.

스케줄러를 만들고 나니 한 가지 케이스가 더 보였다. 주문이 생성되면 도서 재고, 쿠폰, 포인트가 즉시 선점되는데, 결제 화면까지 간 사용자가 결제를 포기하거나 이탈하면 이 자원들이 영영 잠겨버린다. 사용자가 명시적으로 주문 취소를 하지 않는 이상 해제할 방법이 없었다. 그래서 임시방편으로 주문 생성 후 1시간이 지나도 `PENDING` (결제 대기) 상태인 주문을 롤백하는 조건을 추가했다. (지금 생각해보면 주문 생성 흐름에 결제까지 포함되어야 했을 것 같다)

## 4. 사가 유실 방어

초기에는 주문 엔티티 저장과 주문 사가 저장이 별도 트랜잭션으로 나뉘어 있었다. 만약 주문이 저장된 이후 사가 저장이 실패하면 주문만 남고 사가가 없는 상태가 된다. 스케줄러가 나중에 이 주문을 발견해도 사가가 없으니 상태 기반 복구가 불가능해진다.

`OrderInitialCreateService` 클래스에서 주문과 사가 초기화를 단일 트랜잭션으로 묶었다. 어느 시점에 문제가 생기든 두 테이블이 같이 생성되거나 같이 롤백된다.

```java
@Transactional
public OrderInitCreateResult createInitialOrderWithSaga(..., UUID sagaId) {
    Order order = Order.createInitial(...);
    // 주문 아이템, 쿠폰 등 초기화 ...

    orderRepository.save(order);

    OrderCreateSaga saga = OrderCreateSaga.create(sagaId, order.getOrderId());
    orderCreateSagaRepository.save(saga); // 주문과 같은 트랜잭션에서 저장

    return new OrderInitCreateResult(order, saga);
}
```

## 5. 결론

스케줄러를 설계하면서 가장 생각을 많이 했던 부분은 어떤 데이터를 복구 대상으로 삼을지였다. '중단'된 흐름이라는 것은 어떤 것인가? 단순히 `PROGRESS`인 것을 가져오면 정상 처리 중인 흐름을 롤백해버리는 문제가 생기기도 한다. 이번 프로젝트에서는 1분 이상인 `PROGRESS`인 사가만 가져오도록 설정했는데, 1분이 지났다고 정말로 비정상적인 흐름인지 판단할 수 있을까? 어쩌면 네트워크 이슈로 2분, 3분이 걸릴 수도 있을지도 모른다. 

결국 이 스케줄러가 필요해진 것 자체가 분산 트랜잭션의 난이도를 다시 한 번 보여주는 것이라고 생각한다. 모놀리식 환경이었다면 `@Transactional` 어노테이션 하나로 끝났을 일이다. 하지만 분산 환경에서는 사가 패턴을 사용해서 보상 트랜잭션을 구현하고, 그것도 부족해서 스케줄러로 복구해야 하고, 복구를 위해서 상태를 저장해야 했다. 이 복잡한 작업이 오직 주문 생성 하나를 위한 것들이었다.

한 가지 아쉬운 점은 스케줄러 구조가 무한 재시도라는 점이다. 실제로 테스트 중 FK 제약조건 위반으로 보상 트랜잭션이 계속 실패하는 상황이 있었는데, 연동된 메신저로 예외 알림이 새벽 내내 울렸다. 일시적 장애였다면 결국 성공하겠지만, 이렇게 구조적인 이유로 실패하는 사가는 스케줄러가 영원히 재시도하게 된다. 일정 횟수 이상 실패한 사가를 DLQ로 분리해 처리했어야 했다.
